# Known Issues

- **Orchard-to-Ironwood spend is untested against a real Orchard note.** This regtest cannot hold Orchard notes because NU6.3 activates at height 2 (`config/regtest/zebra.toml`), before any block could pay an Orchard receiver. Verified: the Orchard pool chain value is 0 and the Orchard tree `finalState` is `000000` at heights 2, 3 and 113 (`packages/core/tests/logs/p4_followup_orchard_funding.log`). Cited rule, ZIP 258 "Consensus rules from NU6.3 activation" (https://zips.z.cash/zip-0258): "No new value may enter the Orchard pool: for every transaction, vOrchardPoolBalance >= 0 (so the encoded valueBalanceOrchard is nonnegative)" and "A coinbase transaction MUST NOT contain any Orchard-pool Actions; that is, its Orchard component MUST be empty." A funding attempt to an Orchard-only receiver produced 0 Orchard actions and 2 Ironwood actions (`z_sendmany` txid `e1850e719a5fa823c703e361899da40148c246165bfcd19eef4aa7796b001f62`).
- **A real Orchard-note test needs a regtest config where NU6.3 activates after the funding height**, so blocks mined before activation can pay an Orchard receiver and be spent across the turnstile afterwards. That requires a different activation schedule plus a chain wipe, which invalidates the funded state behind the P2/P3 logs. Not attempted.
- **The empty Ironwood root the anchor check compares against is UNVERIFIED against the node.** `ironwood_empty_tree_root()` returns `ae2935f1dfd8a24aed7c70df7de3a668eb7a49b1319880dde2bbd9031ae5d82f` (`orchard::Anchor::empty_tree()`). Zebra's `z_gettreestate` reports **no `ironwood` section at heights 0-1** (pre-NU6.3) and a **non-empty** Ironwood tree at every height from 2 onward, because the first post-activation coinbase already carries an Ironwood action. The node therefore never prints an empty Ironwood `finalRoot` on this chain, so the equality is unverified by direct observation; the empty-node branch of `send()` is covered only by mocked tests. Indirect control: Zebra reports the empty Orchard tree at height 2 as `finalState 000000, finalRoot ae2935f1...`, byte-identical to the helper (`packages/core/tests/logs/ironwood_empty_root.log`).
- **anchor `1c5a7114...` from P1's old chain remains unexplained** and unreproducible; carried over from the P1 review. No committed evidence explains where it came from.
- **The P5 send tests mock proving.** `packages/sdk/src/send.test.ts` Scenarios 1-8 (including the anchor-abort tests 5-7) stub `buildAndProveTransaction`, so they assert reservation, anchor and fee logic but do not run Halo 2 proving. Real proving is exercised only by the Rust builder tests and the live P3 run.
- **Zaino `feat/nu7` experimental tier (pin `aaf8122a703704e05147d984f08ff82c789860ad`).** Zaino's published 0.10.x crates and `dev` branch still carry placeholder branch ID `0xfffffffe` and cannot index past NU7 activation. Branch `feat/nu7` supports NU7 consensus branch ID `0x77190ad9` (built on `zebra-chain 15 / zebra-state 16 / zebra-rpc 19`), but is unreleased upstream. Running `zcash-dev regtest up --stack zaino` builds Zaino from source in Docker using Rust 1.96.0, taking ~3+ minutes on initial run. It is strictly experimental and never the default.
- **Testnet initial wallet sync duration (first-sync from activation height 4,134,000 to tip 4,542,475).** A fresh wallet syncing against public gRPC lightwalletd (`https://testnet.zec.rocks:443`) takes ~22.6 minutes (1,355.5 seconds) to scan 408,475 blocks at an average throughput of ~301.3 blocks/s with 1,000-block batch size and 50 ms throttle pause. Transient HTTP/2 stream drops (`13 INTERNAL: unexpected EOF`) require client retry handling. Full benchmark proof is saved in `packages/core/tests/logs/wallet_b_first_sync.log`.
- **Zallet v0.1.0-beta.4 standalone Zebra backend spike on NU7 regtest (`zodlinc/zallet@sha256:682ba6f9…`).** Verified in `packages/core/tests/logs/zallet_nu7_spike.log` (reproducible configuration committed under `packages/dev/docker/spikes/zallet-beta4/`): Zallet v0.1.0-beta.4 paired directly with Zebra 7.0.0 (configured with `indexer_listen_addr` and shared state volume) successfully follows NU7 regtest, detects Ironwood outputs in `z_listunspent`, and builds/Halo 2 proves/broadcasts v6 Ironwood transactions via `z_sendmany` (txid `30c108ab1881fc8c945f37fb96d4c478230d25c6e951fc402d3b33961769b558`). However: (1) Zallet's distroless Docker image requires an explicit `/tmp` tmpfs mount (`--tmpfs /tmp`) or RocksDB secondary state directory creation fails with `NotFound (os error 2)`; (2) Zallet runs as UID 1000 whereas Zebra runs as UID 10001, requiring `--user 0:0` to read the shared RocksDB state volume; (3) `z_listtransactions` is experimental and fails when reading notes whose memos contain arbitrary non-UTF-8 bytes (such as coinbase notes):
  ```json
  {
    "jsonrpc": "2.0",
    "error": {
      "code": -20,
      "message": "Data DB is corrupted: Invalid memo data: InvalidUtf8(Utf8Error { valid_up_to: 2, error_len: Some(1) })"
    },
    "id": 1793936876172
  }
  ```
  This relates to open upstream issue [Zallet #794](https://github.com/zcash/zallet/issues/794) ("Zallet reports incorrect insufficient balance and wallet DB has invalid UTF-8 memo"). While [PR #866](https://github.com/zcash/zallet/pull/866) addressed `z_listunspent` by omitting unreadable memos instead of failing the request, `z_listtransactions` was not patched and still aborts; (4) `listtransactions` does not exist; (5) the `zaino` backend is completely removed; and (6) the stock `zfnd/zebra:7.0.0` Docker image omits the Cargo `indexer` feature, so Zebra does not write the spending-transaction index on disk; Zallet reads an empty spending index, which disables transparent spend detection, though shielded Ironwood notes and spends are fully tracked through Zebra's core consensus trees.
